Camunda 8 Architecture — Hiểu từ gốc rễ

19/08/2026 · 5 phút đọc · ← Quay lại series

Mục tiêu: Hiểu tổng quan kiến trúc Camunda 8, các component chính và sự khác biệt cốt lõi so với Camunda 7.

Camunda 7 vs Camunda 8 — Không phải nâng cấp, là viết lại

Đây là điều đầu tiên cần nắm rõ vì phần lớn tài liệu trên internet vẫn là Camunda 7. API khác hoàn toàn, đừng học lẫn.

Điểm khác biệtCamunda 7Camunda 8
Process engineInternal (embedded)Zeebe (distributed)
DatabaseMySQL, PostgreSQL...Elasticsearch
Java APIProcessEngine, RuntimeServiceJob Worker
DeployWAR, embedded JARgRPC to Zeebe

Zeebe

Process engine chính — nhận, thực thi, lưu trạng thái process. Giao tiếp với Spring Boot qua gRPC port 26500.

Operate

UI để monitor process đang chạy — xem variables, trace lỗi, resolve incident. Chạy tại localhost:8081.

Tasklist

UI cho User Task — người dùng claim và complete task thủ công. Chạy tại localhost:8082.

Elasticsearch

Không phải database truyền thống — lưu event log của tất cả process instance. Operate và Tasklist đọc từ đây.

Token flow — khái niệm cốt lõi

Trong BPMN, mỗi process instance có một token di chuyển qua các element:

Start Event → Service Task → Gateway → End Event
     ●  ───────────────────────────────────────▶
  • Token đến đâu → element đó active
  • Job Worker nhận job khi token đến Service Task
  • Token tiếp tục khi job được complete

Tóm tắt

  • Camunda 8 dùng Zeebe engine, khác hoàn toàn C7
  • Self-managed gồm: Zeebe + Operate + Tasklist + Elasticsearch + Identity
  • Giao tiếp qua gRPC port 26500, không phải REST như C7
  • Token là đơn vị thực thi trong BPMN
