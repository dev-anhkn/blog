# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static personal engineering blog (dev.anhkn) written in plain HTML - no build tools, no npm, no bundler, no package manager. Styling is **plain CSS** in one shared stylesheet, `shared/theme.css`, loaded via a normal `<link rel="stylesheet">` on every page (see "Styling - Plain CSS" below). The only JS the site ships is one small vanilla-JS file, `shared/site.js`, that every page loads to avoid duplicating the header/footer markup - see "Shared includes" below. Content is in Vietnamese (`lang="vi"`). Focus is a series called **"What I Learned From Course Camunda Academy"** (Java + Spring Boot + Camunda 8 Self-managed) - personal notes written after each lesson from the Camunda Academy course, not a fixed-length "30 day challenge". There is no day-count framing (no "Ngày N/30", no "X ngày" language anywhere) - don't reintroduce it.

## Commands

There is no build/lint/test tooling. Preview by opening the HTML files directly in a browser, or serve the directory statically, e.g.:

```
python3 -m http.server 8000
```

Deployment is via the `origin` git remote (`dev-anhkn/blog`) - pushing to it is presumably what publishes the site (e.g. GitHub Pages), so treat pushes to `main` as publishing live content.

## Structure & conventions

- There is exactly one CSS file in the repo, `shared/theme.css`, loaded via `<link rel="stylesheet">` on every page - see "Styling - Plain CSS" below before writing or editing any markup.
- `index.html` (root) is the homepage; `about.html` is the bio page; `camunda/index.html` is the hub/table-of-contents for the Camunda series; article pages live under `camunda/` (e.g. `camunda/overview.html`, `camunda/introduction.html`). The homepage's "Bài viết mới nhất" card-grid is a separate, hand-maintained list (not auto-generated) showing the 3 most-recently-published articles - when publishing a new article (adding a real card to `camunda/index.html`), also update this homepage section to swap in the new article and drop the oldest of the 3, and update the "N bài viết" count in the homepage's `.spotlight-card` to match the real number of published (non-"Sắp ra mắt") cards in `camunda/index.html`. This list has gone stale before - don't skip it when publishing. Some older files still use a leftover `dayNN.html` name (e.g. `day04.html`, `day06.html`, `day07.html` - none of the three exist as files yet) - that's just a filename, not something to "fix"; new articles can use either a `dayNN.html`-style name or a topic-slug name (preferred, e.g. `overview.html`, `docker-compose.html`).
- Each series is a self-contained top-level folder - the Camunda series lives entirely under `camunda/`: article HTML at `camunda/*.html`, images at `camunda/images/<article-slug>/<file>.png` (one subfolder per article, named after that article's HTML filename, e.g. `camunda/images/bpmn-overview/` holds the images for `camunda/bpmn-overview.html`), and any raw non-HTML source assets (the `.bpmn`/`.dmn` files modeled during the course, not linked from any page) under `camunda/sources/bpmn/` and `camunda/sources/dmn/`. There is no repo-root `images/`, `bpmn/`, or `dmn/` folder anymore - everything Camunda-related was consolidated into `camunda/`. Because images sit alongside the HTML inside `camunda/`, `<img src>` there is just `images/<slug>/<file>` (no `../`) - only links back to root pages (`../index.html`, `../about.html`) need `../`. When a future series starts (non-Camunda content), give it its own top-level folder following this same shape (`<series>/index.html` hub, `<series>/*.html` articles, `<series>/images/<slug>/`, `<series>/sources/` if needed) rather than growing a shared root-level `images/`.
- Image and asset filenames use kebab-case with no spaces or punctuation (e.g. `how-will-this-task-be-completed.png`, not `How will this task be completed?.png`) so URLs never need `%20`/`%3F` encoding. Rename with `git mv` to preserve history when fixing a non-conforming name.
- Nothing in the rendered page shows a day number or "X/30" - the visible `.article-day` badge on each article page shows a **topic label** instead (e.g. `Architecture`, `Docker`, `Spring Boot`, `Giới thiệu`), matching the `.tag` category already used for that article in the card grid. Article titles are plain topic titles (e.g. "Camunda 8 - Overview"), never prefixed with "Ngày N -".
- The series is organized into topic "Phần" (parts) inside `camunda/index.html` (e.g. "Setup & Architecture", "BPMN Cơ Bản"), each holding a `card-grid` of article entries. There is no day-range subtitle under a part heading (no "Ngày 1–7" etc.) - use a short topic description instead, or omit the subtitle. Entries are **not necessarily contiguous or published in file-number order** - e.g. `overview.html` links to `day04.html` as "next" - this is intentional (content is written incrementally); don't "fix" the gaps or treat links to not-yet-written articles as bugs - check with the user before creating placeholder files for them.
- Unpublished/upcoming cards use `style="opacity:0.5; cursor:default; pointer-events:none;"` (or the dashed-border variant on the homepage) instead of a real link, with the `.card-day` badge reading `Sắp ra mắt` instead of a topic. Follow this pattern for new "coming soon" entries rather than linking to a page that doesn't exist yet.
- The header/nav and footer are **not** duplicated by hand - every page has a bare `<header id="site-header"></header>` right after `<body>` and a bare `<footer id="site-footer"></footer>` near the end, and a single `<script src="shared/site.js"></script>` (`../shared/site.js` under `camunda/`) placed right before `</body>` fills both in from JS at load time. It figures out Home/Camunda/About active state from `location.pathname`, and whether the logo should render as a plain `<span>` (on the homepage) or a link back to `index.html` (everywhere else). To change nav links, the logo, or the footer markup/copyright line, edit `shared/site.js` **once** - do not add the old inline `<header><nav>...</nav></header>` markup back into a page. A page-specific footer flourish (the homepage's "Built with ☕...") is passed via `data-tagline="..."` on the `<footer>` placeholder rather than duplicating the whole footer.
- Article pages follow a fixed shape: `.article-header` (topic badge, title, date/read-time meta) → `<nav class="toc">` (table of contents, see below) → `.article-body` (prose, using `.article-body`'s `pre`/`code`/`blockquote`/`table` styles) → `.article-nav` (prev/next links, using the **next article's title**, not a day number - use an empty `<span></span>` on the side that has no neighbor). `.article-nav`'s two links always carry `class="prev"`/`class="next"` and the same inner shape - `<span class="nav-label">← Trước đó</span>`/`<span class="nav-label">Tiếp theo →</span>` followed by `<strong>Article Title</strong>` - never a bare `<a href="...">Title →</a>` (that renders without the "Trước đó"/"Tiếp theo" label or bold title, since `.article-nav a` alone has no such styling). Match this structure for new articles instead of improvising new layout.
- Every article carries a table of contents: `<nav class="toc" aria-label="Mục lục bài viết">` as its own sibling between `.article-header` and `.article-body` (not nested inside either), holding `<p class="toc-title">Mục lục</p>` plus a flat `<ol>` of `<li><a href="#slug">Heading text</a></li>` - **one entry per top-level `<h2>` only**, no nested `<h3>` sub-entries (checked with the user: mục lục should stay to just the numbered top-level sections, 1/2/3/4...). Each linked `<h2>` needs a matching `id="slug"`: lowercase the heading text, strip Vietnamese diacritics (đ→d), collapse everything else to `-`, and drop any leading `"N. "` numbering from the *slug only* - the heading's own visible text keeps its number (e.g. `<h2 id="camunda-8-la-gi">1. Camunda 8 là gì?</h2>`). Everything else is automatic, no extra markup needed. Sidebar placement is pure CSS: `main:has(> .toc)` in `shared/theme.css` grids `<main>` into margin/content/margin columns at `@media (min-width: 1400px)` and puts `.toc` in the left margin as `position: sticky` (falls back to a plain top-of-article block below that width - both states share the same `.toc` styling). `shared/site.js` only wraps everything after `.toc` (i.e. `.article-body` + `.article-nav`) into one `.toc-content-wrap` div so it can be a single grid cell alongside `.toc`, and drives scrollspy (`.active` on the currently-read section's link) via `IntersectionObserver` matched against the TOC's own `href="#..."` targets. Because `.article-header` sits in the *same* grid column as `.toc-content-wrap` on a different row, give it `max-width: none; margin: 0` inside that `main:has(> .toc) > .article-header` rule rather than letting its own base `max-width: 760px; margin: auto` compete with the grid track's width - two independent width calculations that are "supposed" to agree can still disagree in some browsers, which is what caused the article header to render narrower and off-center from the rest of the article on wide screens. A reading-progress bar and a floating back-to-top button are likewise fully automatic on any page with `.article-body` present - no HTML needed for either, and back-to-top doesn't need `.toc` to exist.
- Listing pages (`index.html`, `camunda/index.html`) use the `.card-grid` / `.card` / `.card-day` / `.tag` component pattern for linking to series and articles. Reuse these classes rather than introducing new ones for similar listings. Every real (linked, non-"coming soon") card site-wide - homepage and `camunda/index.html` both - follows this exact anatomy, in this order, inside the `<a class="card">`: `<div class="card-accent"></div>` (a 4px topic-colored top bar) → `<div class="card-icon">` (a 40px badge holding one small inline stroke-based SVG icon, `stroke="currentColor"`, no emoji) → `<span class="card-day">` (the existing pill badge - **keep this**, the icon is additive, not a replacement for it) → `<h3>` → `<p>` → `<div class="card-meta">`. The topic color is set once via an inline custom property on the `.card` itself, e.g. `style="--card-accent: var(--color-blue)"`, referencing one of the secondary palette tokens (`--color-blue`/`--color-green`/`--color-teal`/`--color-yellow`/`--color-purple`/`--color-red`) or `--color-amber` - `.card-accent` and `.card-icon` both read that one property, so set it in one place. Current topic→color assignments (keep new topics consistent with these where they overlap, e.g. any future BPMN-family article stays teal/purple/red like its siblings): Giới thiệu/Introduction=amber, Architecture=blue, Zeebe=blue, Docker=yellow, Spring Boot=green, BPMN(overview)=teal, Task Types=purple, Events=red, DMN=yellow. A "coming soon" disabled card (`style="opacity:0.5; cursor:default; pointer-events:none;"`) never gets `.card-accent`/`.card-icon` - it stays plain. The homepage additionally has a couple of homepage-only components for its sparser content: `.spotlight-card` (a single featured-series card, used in place of a card-grid when there's only one real entry) with its `.series-teaser` (the slim dashed "coming soon" strip below it), and `.quote-strip` (a section rhythm-break band reusing the hero's own tagline). Reuse all of the above on any future listing page before inventing new ones.
- Design tokens (colors, radius, shadows, fonts) live as CSS custom properties in the `:root` block at the top of `shared/theme.css`. Use those custom properties (`var(--color-amber)`, `var(--radius)`, `var(--shadow)`, etc.) instead of hardcoding colors/values - never introduce a new hex color inline in HTML or in a page's `<style>` block.

## Styling - Plain CSS

The whole site is styled with one hand-written, plain CSS file - no Tailwind, no build step, no `npm install`. Every page is fully self-contained.

**The canonical line.** Every HTML file's `<head>` ends with this exact line, immediately before `</head>` (copy it verbatim from any existing page, e.g. `index.html`, when creating a new one):

```html
<link rel="stylesheet" href="shared/theme.css">
```

(under `camunda/`, this is `<link rel="stylesheet" href="../shared/theme.css">`).

Every page's `<head>` also carries a `<meta name="description" content="...">` right after `<title>` - a short (roughly one sentence) summary of that specific page's content, in the same voice as its card blurb on `index.html`/`camunda/index.html` (reuse that exact sentence when one already exists - don't write a new one from scratch). This drives the snippet shown in search results and link-preview cards when the page is shared; every page currently has one, so a new page without it is a gap to fill, not something to skip.

- `shared/theme.css` holds the design tokens (as `:root` custom properties) and every component class (`.card`, `.hero`, `.article-header`, etc.) as ordinary CSS rules. **Edit `shared/theme.css` once** to change a token or a shared component rule; do not paste rules back into individual pages or add per-page `<style>` blocks.
- Component classes (`.card`, `.hero`, `.article-header`, `.article-body`, `.task-card`/`.info-card` accordions, `.lightbox`, `.icon-card-hero` (single centered illustration in a bordered box) / `.icon-card-grid` > `.icon-card` (a grid of small bordered icon+caption boxes, non-collapsible - use these instead of `.task-card`/`.info-card` when the content should always be visible, not click-to-expand), etc.) are defined once in `shared/theme.css` with their original semantic names. **Reuse an existing class** rather than inventing a new one (see `.card-grid`/`.card`/`.tag` reuse rule above) - in particular, don't hand-roll a bordered/centered icon box with inline `style="..."` the way an earlier pass briefly did in `bpmn-participants.html`; that's what `.icon-card`/`.icon-card-hero` are for. A small "small utility helpers" block near the bottom of `shared/theme.css` (`.mb-4`, `.text-center`, `.rounded`, etc.) covers a handful of one-off inline needs - reuse those before adding a new single-purpose class, and prefer a named semantic class over a growing pile of new one-off utility classes.
- `<details>`/`<summary>` accordions (`.task-card`, `.info-card`) use the plain `[open]` attribute selector, and the CSS-only lightbox (`.lightbox`) uses plain `:target` - both are ordinary CSS, no JS involved.
- Opacity-tinted accent colors (badge backgrounds, hover borders, etc.) use `color-mix(in srgb, var(--color-amber) 35%, transparent)` rather than a separate alpha token - follow that pattern instead of hardcoding an `rgba()` value when you need a translucent version of a token color.
- The `camunda/bpmn-events.html` task/gateway/event tab switcher is a CSS-only radio-button component (`.flow-tabs`, `.flow-tab-label`, `.flow-tab-panel` + `#fe-*:checked ~ [data-tab-panel="..."]` sibling-selector rules in `shared/theme.css`). It's one-off and ID-scoped to that page; follow the same sibling-selector pattern (not JS) if a future article needs a similar CSS-only tab switch.

## Shared includes - `shared/theme.css` and `shared/site.js`

A shared CSS file and a hand-written vanilla-JS file at the repo root (`shared/`) are the single source of truth for everything that used to be copy-pasted into every page. Both are loaded relative to the current page (`shared/…` at root, `../shared/…` under `camunda/`), so a new top-level series folder just needs the same `../shared/…` prefix.

- **`shared/theme.css`** - the design tokens + every component class (see "Styling - Plain CSS" above). Linked via `<link rel="stylesheet">` in `<head>`.
- **`shared/site.js`** - fills in the header/nav and footer. Requires two placeholder elements already in the page: `<header id="site-header"></header>` right after `<body>`, and `<footer id="site-footer"></footer>` near the end; the script tag itself goes right before `</body>` (it needs both elements to already exist in the DOM). It derives the correct relative link prefix from its own `src` attribute, decides the active nav link from `location.pathname` (`/camunda/` anywhere in the path → "Camunda" active; `about.html` → "About" active; else "Home"), and renders the logo as a plain `<span>` on the homepage or a link back to `index.html` everywhere else. A `data-tagline="..."` attribute on the `<footer>` placeholder inserts extra text before the GitHub link for a page that wants a custom footer line (only the homepage uses this today). It also handles two small progressive-enhancement effects with no HTML changes required: on any page with an `.article-body` (article pages only), it injects a fixed `#reading-progress` bar that fills left-to-right with scroll position; on every page, it adds a `.reveal` class (styled in `shared/theme.css`) to every `.card`/`.task-card`/`.info-card`/`.spotlight-card` (skipping any that carry an inline `pointer-events: none`, i.e. disabled "coming soon" cards) and flips on `.is-visible` via `IntersectionObserver` as each one scrolls into view, skipped entirely when the visitor has `prefers-reduced-motion: reduce`. Don't hand-write a `#reading-progress` element or `.reveal` classes into page HTML - both are runtime-only, driven from this one file.
- When adding a new page: copy the `<head>` stylesheet `<link>`, the `<header id="site-header"></header>` / `<footer id="site-footer"></footer>` placeholders, and the closing `<script src=".../shared/site.js"></script>` from any existing page - don't hand-write nav or footer markup, and don't add a new top-level nav link without also updating the `link(...)` calls inside `shared/site.js`.

## Design system - "Desert Titan" theme (dark default, light optional)

The site defaults to a dark theme for every first-time visitor, but ships a real light variant too, toggled by a button in the nav (rendered by `shared/site.js`) and persisted in `localStorage` under the key `theme`. Dark stays the baseline experience - light is opt-in, not auto-detected from OS `prefers-color-scheme` (a deliberate choice; don't add a `prefers-color-scheme` media query for this). The dark values live on bare `:root` in `shared/theme.css`; the light values redefine the same custom properties under `:root[data-theme="light"] { ... }` - **always add new tokens to both blocks** (and to any hardcoded override the light block already carries, see below) so a new component doesn't look right only in dark mode.

- **Surfaces** - dark: `--color-surface-0` `#0c0906` (page background) → `--color-surface-1` `#201a11` (cards, header, footer) → `--color-surface-2` `#2e2517` (code blocks, table headers, tags), three-step elevation, darkest at the back. Light: `--color-surface-0` `#faf5ea` → `--color-surface-1` `#f1e6d0` → `--color-surface-2` `#e7d7b3` - same three-step elevation, inverted (lightest at the back).
- **Text** - dark: `--color-text` `#ede0c4` (body/headings) / `--color-text-muted` `#9c8a6a` (secondary/meta). Light: `--color-text` `#2b2013` / `--color-text-muted` `#6e5a3c`. Never pure white/black (`#fff`/`#000`) in either theme.
- **Border**: dark `--color-border` `#453722`; light `--color-border` `#d8c49a`.
- **Accent (amber)**: dark `--color-amber` `#c9872a` / `--color-amber-light` `#e5aa58`; light `--color-amber` `#8a5a1f` / `--color-amber-light` `#a8701f` - deliberately darker in light mode so amber text/links keep enough contrast against the light surfaces (the raw dark-mode amber fails contrast on a light background). For a translucent version of a token color, use `color-mix(in srgb, var(--color-amber) 14%, transparent)` (bg tint, 12–15%), `color-mix(in srgb, var(--color-amber) 35%, transparent)` (border overlay), `color-mix(in srgb, var(--color-amber) 45%, transparent)` (hover border, e.g. on card hover) - don't hardcode a separate `rgba()` value; this scales automatically to whichever theme's `--color-amber` is active.
- **Secondary palette** (reserve for category tags / status colors, not yet wired to specific components, dark values - not yet given light-mode equivalents since nothing uses them yet): `--color-blue #7699b8`, `--color-green #7aa86a`, `--color-teal #5a9a88`, `--color-yellow #c9a030`, `--color-purple #a88888`, `--color-red #c05a40`.
- **Radius**: `--radius` 12px (cards, nav links) / `--radius-chip` 8px (buttons, code blocks, blockquote) / `--radius-pill` 20px (badges) / `--radius-tag` 4px (tags, inline code) - same in both themes.
- **Shadow**: dark `--shadow` = `0 1px 0 rgba(255,255,255,0.04) inset, 0 2px 12px rgba(0,0,0,0.6)`, `--shadow-hover` = `0 1px 0 rgba(255,255,255,0.06) inset, 0 8px 32px rgba(0,0,0,0.6)`. Light `--shadow` = `0 1px 0 rgba(255,255,255,0.6) inset, 0 2px 12px rgba(90,70,40,0.16)`, `--shadow-hover` = `0 1px 0 rgba(255,255,255,0.7) inset, 0 8px 28px rgba(90,70,40,0.22)` - a warm-brown-tinted shadow rather than black, to match the light palette's tone.
- **Font**: `--font-sans` = Inter (loaded via a CSS `@import` at the top of `shared/theme.css`, falls back to `system-ui`) and is applied once on `body`, so most elements need no font override. `--font-mono` = `'JetBrains Mono', 'Fira Code', 'Cascadia Code', monospace` for code. Body `line-height: 1.625`.
- **Headings**: only `.hero h1` (the homepage hero) renders as an actual gradient, via `background-image: linear-gradient(to bottom right, #f5e8cc, var(--color-amber-light)); background-clip: text; color: transparent;`. `.page-header h1` and `.article-header h1` are **not** gradient text despite looking similar - they're plain solid `color: var(--color-text)`, same mechanism as any other heading. Don't add `background-image`/`background-clip` to those two selectors (a earlier pass briefly did, by mistake, for the light theme - it painted a visible rectangular gradient box behind the opaque heading text, since there was no `color: transparent` to clip it to the letterforms). The `#f5e8cc` gradient stop on `.hero h1` is a hardcoded light color tuned for a dark backdrop, not a token, so it's unreadable as-is on the light theme - `shared/theme.css` overrides just `.hero h1`'s `background-image` under `:root[data-theme="light"]` with `linear-gradient(to bottom right, #3a2a14, var(--color-amber-light))` instead. Keep both the dark base rule and this light override in sync if the gradient design changes. H2 (`.article-body h2`) is `font-size: clamp(1.4rem, 3vw, 2rem); font-weight: 700;` with a 14%-amber underline (`color-mix(in srgb, var(--color-amber) 14%, transparent)`) - token-based, so it adapts to either theme with no override needed.
- **Hero background**: a plain CSS `background:` declaration combining a radial amber glow with a `linear-gradient(160deg, ...)` base; the one deliberate hand-written gradient in `.hero` rather than a token, using hardcoded dark hex stops (`#2a1e0a`, `#1a1508`). Because those stops aren't tokens, `shared/theme.css` also carries a `:root[data-theme="light"] .hero` override with light-appropriate stops (`#f2e6cd`, `#ecd9b1`) and a softer-opacity radial glow - keep both in sync together.
- **Layout**: `.container`/`nav` are `max-width: 1200px; margin: 0 auto;`; `.card-grid` is `grid-template-columns: repeat(auto-fit, minmax(260px, 1fr))`; `.section` is `padding: 4rem 0`. Article reading columns (`.article-header`/`.article-body`/`.article-nav`) stay narrower at `max-width: 760px` for readability - don't widen those to 1200px.

**The theme toggle.** `shared/site.js` renders a `.theme-toggle` button (☀️/🌙, styled in `shared/theme.css`) into the nav next to the links, reading/writing `localStorage.theme` (`"light"` or absent/anything else = dark) and flipping `data-theme="light"` on `<html>`. Because `site.js` only runs near the end of `<body>`, applying the stored preference there alone would flash dark-then-light on every load for light-theme users - so every page's `<head>` also carries a tiny inline **theme-init script**, immediately after `<meta charset="UTF-8">`, that must run before first paint:

```html
<script>try{if(localStorage.getItem("theme")==="light")document.documentElement.setAttribute("data-theme","light")}catch(e){}</script>
```

Copy this verbatim (same on every page, no `../` prefix needed since it only touches `localStorage`/`document`) into any new page's `<head>`, right after the charset meta and before the viewport meta - same "copy this exact line" treatment as the `theme.css` `<link>`.

When adding new components, pull colors/radii/shadows from the CSS custom properties in `shared/theme.css` rather than hardcoding hex values or arbitrary one-off colors, so the whole site stays visually consistent with this palette **in both themes** - check any new component in light mode too, since a few high-signal spots (heading gradients, `.hero` background) intentionally bypass tokens and need an explicit `:root[data-theme="light"]` override rather than adapting for free.
